# WBC source discrepancy and proposed resolution

Status: concrete proposal for approval; no implementation changes or runtime checks performed.

## B01: the local source gives conflicting schedules

Authority: `papers/summary/papers/wbc.pdf`, Chen et al., arXiv:2601.02751v2, 5 March 2026, §4.1.4 Eq. (12), §5.3.2, Appendix C.1.5 p. 23. The corresponding written-paper copy contains the same contradiction. The printed appendix was visually checked.

Eq. (12), with ten sizes from 2 to 40, evaluates to:

`[2, 3, 4, 5, 8, 11, 15, 21, 29, 40]`

The appendix's literal experimental list is:

`[2, 3, 4, 6, 9, 13, 18, 25, 32, 40]`

These cannot be reconciled by an ordinary rounding convention. Selecting one changes the procedure; it is not cleanup. The user authorized continuing the audit with the discrepancy recorded.

## Evidence supporting a practical choice

The authors' example configuration specifies the appendix's literal list. Their scoring code calculates a fraction separately for each size and then averages those fractions. It clamps a requested size to the sequence length for short inputs. These observations corroborate an experimental implementation, rather than correcting the paper by themselves. [Author configuration](https://raw.githubusercontent.com/Stry233/WBC/main/configs/example.yaml), [author scorer](https://raw.githubusercontent.com/Stry233/WBC/main/attacks/wbc.py).

The final USENIX paper retains the geometric equation and uniform aggregation; the conflicting literal appendix passage is absent. That version therefore does not prove which schedule generated the earlier results. It must not silently replace the user's local v2 authority. [Final paper](https://www.usenix.org/system/files/usenixsecurity26-chen-yuetian.pdf).

The inspected upstream URLs point to mutable `main`; no immutable commit was successfully resolved during this audit. Pin and archive the chosen upstream revision before the remote reproduction. Do not represent these links as immutable evidence.

## Proposed resolution

1. **Use the appendix's explicit list for the reproduction configuration**, named in metadata as `local-v2-appendix-author-config`. It is already the local implementation's default, so this choice avoids an unsupported schedule change. Replace the inaccurate claim that this exact list is generated by Eq. (12).
2. **Correct aggregation under either schedule:** compute the positive fraction for each size, then average fractions uniformly. This is required by local Eq. (13)/Algorithm 1 and independent of B01.
3. **Evaluate Eq. (12)'s list as a separately identified sensitivity run**, on the same target/reference checkpoints and candidate scores. Prespecify this comparison; do not choose the reported schedule using test AUC.
4. **Use candidates with at least 40 scored tokens for the first fidelity check.** This avoids conflating schedule/aggregation with the separate short-sequence policy. If reproducing upstream short-input handling later, explicitly implement and record clamping, including repeated effective sizes. Skipping, clamping and rejecting are not equivalent.
5. **Keep B01 marked as a source discrepancy.** Exact experimental attribution requires an author clarification or immutable experimental artifact. The operational choice above is defensible and reproducible, but is not proof that the contradictory statements agree.

Suggested clarification to the authors, drafted only and **not sent**: “For arXiv v2 Eq. (12), w_min=2, w_max=40, K=10 produces [2,3,4,5,8,11,15,21,29,40], while Appendix C.1.5 and the public example config specify [2,3,4,6,9,13,18,25,32,40]. Which schedule generated the reported tables, and is either statement an erratum? Please identify the experimental code revision and intended short-sequence policy.”

## Discriminating acceptance check

| Quantity | Value |
|---|---:|
| Size-1 positive fraction | 1/3 |
| Size-3 positive fraction | 0 (sum is exactly zero) |
| Eq. (13) uniform mean | **1/6** |
| Current pooled score | **1/4** |

Use this tiny analytical fixture on the remote server after approval; it tests aggregation, not the recommended experimental sizes. Zero-sum windows must not count as positive. Add all-positive/all-negative/tied windows, invalid sizes, duplicate sizes and short inputs with the explicitly chosen policy. Require identical token events under target/reference before subtracting their losses.

For the scientific rerun, retain per-size rates and the final score, schedule identity, effective sizes, target/reference and tokenizer revisions, effective token spans, split hashes and method version. Reuse cached **raw aligned token losses** only when those identities agree; never reuse the old pooled final scores as corrected results.
